# Operator HTTPS acceptance gate

`npm run test:operator:acceptance` runs the bounded synthetic end-to-end acceptance scenario through the same isolated Auth and Firestore emulator runner used by the operator backend tests. It requires the dedicated `demo-patternly-ops-b4` project and the runner's fixed loopback ports; the runner refuses unexpected projects, occupied ports, or a non-loopback emulator configuration.

The scenario talks to the running Fastify app through a real local HTTPS proxy with a trusted ephemeral test certificate. It uses actual Firestore stores and the production RS256 OIDC verifier with a generated test key and controlled JWKS response. Public intake, email verification and email delivery use isolated fixtures. The fixture does not represent a production identity provider or email delivery claim, and it creates no cloud resources.

For each of the four request families, the gate verifies a stale status/revision compare-and-set returns a conflict without changing state or audit count. It also commits one action, drops its response, and checks the CLI reports an ambiguous outcome after exactly one PATCH and two GETs: the precondition read and one reconciliation read. It verifies the persisted postcondition and exactly one corresponding action audit. Operator audit rows must contain the exact actor HMAC derived through the verifier and family-specific store rule; public privacy intake audit markers are checked separately. Both operator bearer tokens must be absent from queue output and serialized audit records. The gate also covers public content, privacy and legal intake; list, detail and action flows; read-only operator denial; security incident idempotency; and redaction of detail narratives from queues, email addresses and encrypted artifacts from CLI projections, and test identities, narratives, recipient addresses, and incident title/details from audit records. Security audit records may retain restricted assessment-state snapshots; the gate allows those scalar state fields while excluding incident narrative, title/details, and recipient addresses. Privileged detail views deliberately include their approved narrative/context fields. The gate confirms the Auth and Firestore emulator SDK connections and the live HTTP/TLS health and readiness endpoints before creating acceptance data.

The acceptance test is also part of `npm run ci`. It is deliberately separate from the general emulator suite so it can retain its dedicated project, ports and fail-closed runner checks. Run it with its package script rather than invoking the test file directly; a direct run without the gate environment is reported as skipped.

The local test runner requires Node.js 22.19 or later for the test-only default CA trust helpers (`node:tls` `getCACertificates` and `setDefaultCACertificates`). This does not raise the backend runtime's production minimum, which remains Node.js 22. The CI Node pin must meet the test-only requirement.
