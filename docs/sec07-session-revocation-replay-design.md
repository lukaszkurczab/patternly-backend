# SEC-07 / prompt 12 — projekt retencji i ochrony replay

**Status:** PASS projektu w granicy przed pierwszą premierą iOS, niezależny review `gpt-6-luna high` z 14.10.2026; implementacja należy do promptu 13. Bez zmiany kodu, konfiguracji Firestore i usług. Decyzja właściciela z 07.10.2026 ustala 30 × 24 h dla potwierdzonego zakończenia. Niniejszy projekt wybiera sposób rozpoznania starego żądania po fizycznym TTL delete.

## Bieżący kontrakt i luka

- `POST /v1/account/session/revoke` przyjmuje UUID `operationId` od klienta, po App Check i bearer. Klient zapisuje ID w lokalnym pending revoke, ponawia ten sam ID po restarcie, a po otrzymaniu tokenu zastępczego loguje się nim i usuwa lokalny pending marker (`AccountSessionProvider.tsx`, `pendingSessionRevocation.ts`). Obecny generator zwraca UUIDv4; `localLogoutControl.ts` dopuszcza **wyłącznie v4** przy odczycie, zapisie, clear i completion. Nowy v7 bez zmiany tego walidatora zepsułby trwałą kolejkę.
- `revokeSessions` czyta użytkownika i dokument `sessionRevocationOperations/{operationId}` w transakcji. `pending` blokuje równoległego właściciela, `failed` może ponowić revoke, `revoked` pomija revoke i ponawia `createCustomToken`. Po udanym revoke kod **nie zwiększa** `authorizationGeneration`: token zastępczy ma tę samą generację. Kontrola bieżącej generacji odrzuca zmianę generacji, lecz sama nie rozpozna starego ID po TTL delete.
- Obecny dokument zawiera `operationId`, `userId`, `expectedAuthorizationGeneration`, `status`, `updatedAt` i ewentualnie `failureCode`; nie ma `expiresAt`. Konfiguracja TTL nie obejmuje `sessionRevocationOperations`. Usunięcie konta usuwa należące dokumenty tej kolekcji.

## Porównanie najmniejszych mechanizmów

| Mechanizm | Po fizycznym delete | Koszt i granica danych | Ocena |
| --- | --- | --- | --- |
| Samo `expiresAt`/TTL albo sama bieżąca generacja | Brak rekordu wygląda jak pierwsze żądanie; revoke nie zmienia generacji | Mała zmiana, ale narusza AC | Odrzucony |
| Trwały indeks zużytych UUIDv4 | Rozpoznaje dowolnie stare ID | Osobna kolekcja i identyfikatory utrzymywane po 30 dniach, decyzja o nieograniczonej retencji i czyszczeniu konta | Odrzucony |
| Zwiększanie generacji przy revoke | Stare żądanie traci uprawnienie | Zmienia cały przepływ auth i wydawania tokenu, wymaga koordynacji z klientem/recovery | Odrzucony w SEC-07 |
| Server-issued podpisany ID z czasem | Stary ID ma weryfikowalny wiek | Nowy endpoint/sekret, rotacja klucza i dodatkowy handoff klienta | Odrzucony jako większa zmiana |
| **UUIDv7 z czasem w samym ID** | Brak rekordu + stary ID jest odrzucany przed skutkiem | Bez dodatkowego rekordu ani dłuższej retencji; wymagany nowy generator klienta, walidacja i świadoma obsługa legacy UUIDv4 | **Wybrany** |

## Wybrany kontrakt

1. Nowe żądania używają kryptograficznie losowego UUIDv7, którego wbudowany czas w milisekundach pochodzi z zegara klienta. `localLogoutControl.ts` musi walidować v4 **i** v7 w całym cyklu: parse, queue, clear, completion; zapisane v4 pozostają byte-identical i czytelne. Lokalny pending marker utrwala **dokładnie** to ID; retry nigdy nie generuje kolejnego ID samoczynnie. API nie przyjmuje osobnego, edytowalnego pola czasu. Zmiana bitów czasu zmienia operation ID, więc nie jest retry tego samego żądania. Przypięty Zod 3.25.76 przyjmuje oba warianty przez `.uuid()` (lokalny probe z 14.10); prompt 13 ma utrwalić to w testach trasy, bez zmiany schematów pozostałych operacji.
2. W tej samej transakcji, która może przejąć slot i zapisać `pending`, backend odczytuje dokument ID i pobiera jedną wartość `now` dla decyzji. Jeśli dokument istnieje, najpierw sprawdza powiązanie z `userId` i oczekiwaną generacją. Dla `revoked` sprawdza niezmienny `expiresAt` **przed** możliwością `createCustomToken`; od `expiresAt <= now` odmawia. Wyłącznie zapisane `pending` i `failed` pozwalają na dotychczasową bezpieczną kontynuację bez ograniczenia wieku ID. Nieznany status, błędny kształt lub `revoked` bez wiarygodnych terminalnych pól odmawia przed revoke i mint, nigdy nie wpada w domyślną gałąź `pending`. Nie stosuje ponownie bramki pierwszego użycia do istniejących poprawnych operacji.
3. Jeśli dokumentu **nie ma**, pierwsze przejęcie akceptuje tylko UUIDv7 z czasem `issuedAt` w domkniętym przedziale `[now - 29 × 24 h, now + 5 min]` (`issuedAt < now - 29 dni` i `issuedAt > now + 5 min` są odrzucane). Sprawdzenie następuje przed odczytem tożsamości/efektem providera. Każdy UUIDv4 przy braku dokumentu, zbyt stary UUIDv7, przyszły ponad 5 min, błędna wersja/wariant i uszkodzony ID dostają jawny błąd operacji wygasłej/nieobsługiwanej, bez zapisu slotu, revoke i grantu. Nowe ID z aktualnym czasem to nowa świadoma operacja, nie automatyczny retry. Sprawdzanie to jest granicą **pierwszego użycia**, nie TTL dla istniejącego `pending` lub `failed`.
4. Po potwierdzonym revoke transakcja finalizacji zapisuje `status: revoked`, niezmienny `terminalAt` i **dokładnie** `expiresAt = terminalAt + 30 × 24 h`, usuwa `failureCode` i zwalnia slot. Odczyt terminalny wymaga poprawnych timestampów i tej równości; nieprawidłowy rekord odmawia grantu. Błąd późniejszego `createCustomToken` pozostawia `revoked` do retry; nie ponawia `revokeRefreshTokens`, nie przepisuje `terminalAt`/`expiresAt`. Przed `expiresAt` zgodny UID i bieżąca generacja mogą ponawiać wydanie tokenu. Od `expiresAt` brak grantu, nawet gdy TTL jeszcze nie usunął dokumentu. Po fizycznym delete reguła punktu 3 odrzuca dokładnie stare ID. Dowód zakłada, że tylko ten writer/backfill nadaje terminalne `expiresAt`; ręczne przedwczesne skasowanie dokumentu albo zapis wcześniejszego TTL poza kontraktem wymaga odrębnego przeglądu.
5. `pending` i `failed` nie dostają `expiresAt`; lease/fence pozostają ochroną współbieżności, nie terminem retencji. Jeśli provider potwierdzi revoke, ale finalizacja nie utrwali `revoked`, to nadal istniejący rekord jest ponawialny według obecnego kontraktu i może wykonać revoke ponownie; to odrębna granica niepewności zewnętrznego skutku, której ten projekt nie usuwa. Zmiana generacji konta lub usunięcie konta odrzuca stary request przed tokenem.

**Uzasadnienie granicy 29 dni:** pierwszy zaakceptowany UUIDv7 może mieć znacznik maksymalnie 5 minut późniejszy niż czas przejęcia. `terminalAt` nie może być wcześniejszy niż przejęcie. Fizyczny TTL delete po `terminalAt + 30 dni` następuje więc, gdy wiek ID wynosi co najmniej `30 dni - 5 minut`, już poza 29-dniowym oknem pierwszego użycia. Jawne założenie platformy: zegary backendu zapisującego `terminalAt` i odczytującego późniejsze żądanie oraz zegar usługi TTL nie rozchodzą się w sposób, który znosi zapas 23 h 55 min. Bieżący kod nie ma niezależnego źródła czasu pozwalającego wykryć duży skok/rollback zegara backendu; projekt **nie obiecuje** fail-closed przy takim zdarzeniu. Jest to pozostające ryzyko infrastrukturalne do oceny przy implementacji. TTL jest asynchroniczny; logiczna granica `expiresAt` obowiązuje niezależnie od jego opóźnienia.

**Migracja UUIDv4 i starszych rekordów:** istniejący dokument v4 `pending`/`failed`/niewygasły `revoked` zachowuje retry, a lokalny dual-format parser zachowuje istniejące markery. Dla istniejących `revoked` bez `terminalAt/expiresAt` wolno jednokrotnie wyprowadzić te pola z `updatedAt` tylko dla zweryfikowanego obecnego kształtu rekordu: w bieżącym kodzie `updatedAt` terminalnego `revoked` jest zapisany podczas finalizacji i nie jest aktualizowany przez retry. Brak wiarygodnego czasu lub nieznany kształt zatrzymuje migrację tego rekordu i odmawia wydania tokenu do ręcznego rozstrzygnięcia; nie ustawia nowego 30-dniowego okresu od daty backfillu. Prompt 13 musi najpierw zrobić inventory starszych rekordów i potwierdzić tę przesłankę, a następnie test migracji. Po fizycznym usunięciu ten sam v4 jest odrzucany. Lokalny v4 zapisany offline bez dokumentu nie może rozpocząć operacji po wejściu nowego kontraktu; klient musi pokazać jawny stan i umożliwić użytkownikowi świadomy restart z nowym v7, bez cichej zamiany ID lub skasowania danych.

**Wdrożenie przed pierwszą premierą iOS:** obowiązujący plan stwierdza brak rzeczywistych użytkowników i danych produkcyjnych oraz brak wymogu zgodności starych lokalnych buildów. Prompt 13 musi dostarczyć backend i klienta v7 jako jeden spójny lokalny pakiet, zachowując odczyt istniejących markerów v4, a testy wykonywać na nowym kliencie. Nie przełączać samego backendu w środowisku obsługującym stary, wspierany build v4; przed pierwszą premierą taki build nie jest wspieranym kanałem. Jeśli dystrybucja starych wspieranych buildów pojawi się przed wdrożeniem lub kontrakt będzie wdrażany po premierze, potrzebny jest osobny minimal-version/negotiation gate i ponowny review; obecny projekt nie zakłada atomowego App Store rollout.

## Retencja i dane

| Dane | Okres i powód |
| --- | --- |
| `operationId` jako ID dokumentu, `userId`, `expectedAuthorizationGeneration`, `status`, `terminalAt`, `expiresAt` (oraz `updatedAt`, jeśli potrzebne do diagnostyki) | Terminalny `revoked`: do fizycznego TTL delete po niezmiennych 30 × 24 h; UID/generacja wiążą retry, status i czas zapobiegają ponownemu revoke/grantowi. Po logicznym wygaśnięciu odczyt odmawia niezależnie od opóźnienia TTL. `updatedAt` nie jest podstawą retencji i retry go nie aktualizuje. |
| `operationId`, `userId`, generacja, `status`, `updatedAt` i ograniczony `failureCode` | `pending`/`failed`: bez arbitralnego TTL, dopóki operacja może wymagać ponowienia; usunięcie konta usuwa rekord. Nie przechowywać tokenu, surowego Firebase subject ani dodatkowego indeksu UUID. |
| Lokalny pending marker z UID i ID | Do udanego zastępczego logowania i lokalnego ACK; jeśli stary ID zostanie odrzucony, pozostaje jawnie nierozwiązany do świadomej decyzji użytkownika. Polityka retencji lokalnego markera nie jest zmieniana w tym wycinku. |
| Firestore PITR/kopie i logi | Retencja terminalnego dokumentu nie oznacza natychmiastowego usunięcia kopii. Istniejący runbook opisuje PITR osobno; prompt 13 ma uaktualnić macierz dla nowej kolekcji, a odbiór rzeczywistej TTL należy do R04/ODK-E2E-082. |

## Tabela granic do implementacji i odbioru

| Stan przy retry | Wynik bezpieczny |
| --- | --- |
| Istnieje `revoked`, `now < expiresAt`, zgodny UID/generacja | Tylko `createCustomToken`; bez drugiego revoke i bez zmiany `terminalAt`/`expiresAt`. Jeśli mint zawiedzie, ten sam stan pozostaje. |
| Istnieje `revoked`, `now >= expiresAt`, TTL jeszcze nie usunął | Jawna odmowa; zero revoke i zero grantu. |
| `revoked` fizycznie usunięty przez TTL | Stary v7 przekracza 29-dniowe okno; stary v4 nie może być pierwszym użyciem. Odmowa przed slotem/providerem nawet przy nadal bieżącej generacji. |
| `createCustomToken` nie powiódł się po `revoked`; retry po logicznym terminie lub TTL delete | Odmowa bez nowego revoke i bez nowego grantu. Lokalny pending marker pozostaje jawnie nierozwiązany do świadomej decyzji. |
| Istnieje `pending` lub `failed`, dowolnie stary ID, zgodny UID/generacja | Dotychczasowy lease/fence i retry; brak arbitralnego TTL. |
| Brak rekordu, nowy v7 w oknie, bieżąca generacja | Jedno nowe przejęcie; równoległy request widzi ten sam rekord/slot. |
| Brak rekordu, v4 albo stary/przyszły v7 | Jawna odmowa; bez revoke, mint i nowego rekordu. |
| Istnieje dokument innego UID/generacji albo konto zmieniło generację/zostało usunięte | Konflikt/odmowa; brak grantu. |
